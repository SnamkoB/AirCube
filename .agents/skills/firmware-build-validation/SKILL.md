# Firmware Build Validation

Read this entire `SKILL.md` before applying it. Also read `../../../docs/build_and_test.md`, `../../../docs/known_issues.md`, and `../../../docs/progress_tracker.md` completely.

## Mandatory outcome

After working on product code, always perform the relevant code-specific checks and a clean firmware build before declaring the task complete. Inspect the complete build output for warnings and errors, repair code-caused or actionable findings, rebuild until clean, generate the merged binary, and publish it to:

`../../../output/firmware/AirCube_firmware_v<version>.bin`, where `<version>` is read from `../../../firmware/version.txt`.

Never claim success or publish a new artifact when a command failed, warnings remain unexplained, the merged image is stale, or required validation could not run. Documentation-only and skill-only changes do not require a firmware rebuild unless they alter commands or build configuration.

## Verified environment

- Project directory: `../../../firmware/` relative to this skill.
- Target: ESP32-H2, 2 MB flash.
- Verified SDK: ESP-IDF v6.0.2.
- Required managed components: `esp-zboss-lib` 1.6.4 and `esp-zigbee-lib` 1.6.7.
- On this Windows machine EIM is normally at `%LOCALAPPDATA%\Microsoft\WinGet\Links\eim.exe`.
- The local EIM v5.3.4 compiler extraction was missing `cc1.exe`; do not use that installation unless it has been independently repaired and compiler-tested.

Use an already activated ESP-IDF v6.0.2 terminal when available. Otherwise run commands through EIM:

```powershell
$ErrorActionPreference = 'Stop'
$eim = "$env:LOCALAPPDATA\Microsoft\WinGet\Links\eim.exe"
& $eim list
if ($LASTEXITCODE -ne 0) { throw "Unable to list ESP-IDF installations" }
& $eim run "idf.py --version" v6.0.2
if ($LASTEXITCODE -ne 0) { throw "ESP-IDF v6.0.2 is unavailable" }
```

## Build procedure

1. Inspect current changes and determine additional checks needed for Python, JavaScript, Lua, protocols, or integrations. Firmware compilation does not validate those clients.
2. Verify `../../../firmware/version.txt`, `../../../firmware/main/idf_component.yml`, target, and intended ESP-IDF version. Do not upgrade dependencies merely to make a build pass.
3. Ensure the repository-root artifact directory exists: `output/firmware/`. This directory is generated output and ignored by Git.
4. From `firmware/`, run a clean ESP32-H2 build. Preserve the complete console output in `../output/firmware/build.log`.
5. Check the command exit code. Then search the full log case-insensitively for `warning:`, `error:`, `FAILED`, linker failures, partition overflow, dependency substitutions, and deprecation diagnostics.
6. Diagnose every finding. Repair source/build configuration when safe and in scope. Do not suppress warnings without proving the code is intentional and safe.
7. Repeat the clean build after repairs. An incremental build alone is insufficient for final warning validation because unchanged files may hide earlier diagnostics.
8. Confirm `../../../firmware/dependencies.lock` resolves ZBOSS 1.6.4, Zigbee 1.6.7, and the intended ESP-IDF version.
9. Run `idf.py merge-bin` only after the build passes review. Confirm `build/merged-binary.bin` was regenerated by this run and reports readiness for offset `0x0`.
10. Copy the merged image to `output/firmware/AirCube_firmware_v<version>.bin`. Replace that versioned destination only after all prior steps pass.
11. Verify the copied file exists, is non-empty, matches the source size and SHA-256 hash, and record image/app sizes plus partition headroom.
12. Run hardware smoke tests when hardware is available. A successful compile does not prove sensor, BLE, Zigbee, USB, flash, or runtime behavior.

## Warning and repair policy

- Zero unexplained compiler/linker warnings is the target.
- Existing warnings are not automatically acceptable. Investigate and repair them or document a justified decision; do not suppress them merely to pass the build.
- Distinguish project diagnostics from SDK/toolchain diagnostics, but record both. Repair project findings; document external findings and their impact.
- Never edit generated files under `../../../firmware/build/`, `../../../firmware/managed_components/`, `../../../firmware/sdkconfig`, or `../../../firmware/dependencies.lock` as the source fix.
- Never switch to Zigbee library 1.6.8; repository evidence records an ESP32-H2 PHY startup hang.
- Do not flash hardware unless the user requests it or flashing is explicitly part of the task.

## Windows command pattern

On Windows, read and follow `references/windows-build.md` completely. It contains separate fail-fast build, merge, review, and publication blocks. Never combine them in a way that bypasses either complete-log stop gate. Its diagnostic patterns are a minimum gate, not a substitute for reading the logs.

## Completion record

Report exact SDK/component versions, commands, build result, every warning/error and disposition, output path, binary size/hash, partition headroom, and hardware tests performed or omitted. Update `../../../docs/build_and_test.md` when the workflow or verified baseline changes and append meaningful results to `../../../docs/progress_tracker.md`.
