# AirCube-TinieTronics Repository Documentation Task

You are working in the checked-out **AirCube-TinieTronics** repository.

This project is a fork of the upstream AirCube project:

`https://github.com/StuckAtPrototype/AirCube`

The checked-out AirCube-TinieTronics repository, its current branch, and its current files are the source of truth. Use the upstream repository only as supporting context. Do not assume that behavior in the fork is identical to upstream.

## Primary objective

Analyze and document the repository so that future AI agents can quickly:

1. Understand the project and its architecture.
2. Locate relevant source files and documentation.
3. Build, test, debug, and safely modify the project.
4. Understand important design decisions, constraints, protocols, and known issues.
5. Continue previous work without repeating repository discovery.
6. Maintain and improve the documentation and project-specific Agent Skills.

This task is primarily a documentation and knowledge-preservation task. Do not implement unrelated features or change product behavior.

## Mandatory startup procedure

Before writing documentation:

1. Inspect the repository root and all tracked files.
2. Record:

   * Current branch.
   * Current commit hash.
   * Configured Git remotes.
   * Whether the working tree already contains uncommitted changes.
3. Read all existing repository documentation before creating replacements.
4. Inspect existing agent instruction files and skill directories, including locations such as:

   * `AGENTS.md`
   * `CLAUDE.md`
   * `.agents/`
   * `.claude/`
   * `.github/`
   * `docs/`
5. Identify build files, dependency files, CI workflows, test configurations, release scripts, hardware files, protocol definitions, and generated artifacts.
6. Use `git ls-files` or an equivalent repository-aware method so that important tracked files are not missed.

Do not overwrite useful existing documentation without first understanding and preserving its relevant content.

## Repository-analysis scope

Analyze all tracked, human-maintained repository content, including where applicable:

* Firmware and embedded code.
* Home Assistant, Zigbee, BLE, SmartThings, or other integrations.
* Build systems and dependency configuration.
* CI/CD and release workflows.
* Tests and validation utilities.
* Documentation.
* Development tools and helper scripts.

For large binary, generated, manufacturing, or CAD artifacts:

* Catalogue their location and purpose.
* Identify which source files generate them when possible.
* Do not claim to have deeply inspected a format that available tools cannot reliably read.
* Clearly distinguish verified information from inference.

## Evidence and accuracy requirements

Documentation must be grounded in the repository.

When describing an implementation:

* Reference relevant repository paths.
* Reference important functions, classes, tasks, components, protocols, or configuration sections when useful.
* Distinguish between:

  * Verified behavior.
  * Inferred behavior.
  * Unverified or unknown behavior.
* Do not copy outdated documentation without checking it against the current source.
* Do not claim that a build, test, or command succeeded unless it was actually run successfully.
* Record commands that could not be run and explain why.
* Do not expose secrets, credentials, private keys, tokens, or sensitive local configuration.

## Documentation-size policy

The most important information in every documentation file and every `SKILL.md` must appear within the first 100 lines.

Use the following maintainability guidelines:

* Keep overview and instruction files concise.
* Prefer focused documents over very large mixed-topic documents.
* Consider splitting a document when it exceeds approximately 300–400 lines, contains multiple independent topics, or becomes difficult to scan.
* Put summaries and navigation first.
* Move detailed tables, protocols, examples, or historical material into linked supporting files.
* Remove accidental duplication, but preserve unique reasoning, decisions, and discoveries.
* Update all incoming links after moving or renaming content.

These are maintainability guidelines rather than permission to omit necessary information.
